# The Queue holds a Feature that waits on another

Every Feature branches from the base branch, as every coding agent we compared does (`docs/research/feature-queue-branching.md`). A Ticket blocked by an open item outside its own Feature, such as a Ticket of another Feature whose pull request is not merged yet, cannot be built on that branch. Today such a Feature is still claimed, built up to that Ticket, and opened as a partial draft pull request. Instead, `--once` and `--watch` hold it: they skip it, keep its Go, take the next Feature in the Queue, and take it again on a later poll once nothing outside holds it. A Feature is held while one of its open Tickets with the ready Signal has an open blocker that is not a Ticket of the same Feature; a lone issue is held while it has an open blocker. The hold is worked out from the blocking links on each read, never stored, so it needs no new Signal and no tracker state (ADR 0002). A held Feature shows in Waiting on you with the blocker it waits for, since a person merging that blocker is what frees it. `nightjar <id>` still builds a held Feature, because a person named it.

## Considered Options

- **Build up to the blocked Ticket (today).** Rejected: the draft pull request is partial, and a person must give the Go again after merging the blocker, so the Queue does not run on by itself.
- **Stack the Feature on the blocker's branch.** Deferred: the child must be rebased whenever the parent gets a Feedback round or a Pull-check fix, which force-pushes under a reviewer (ADR 0004); `git rebase --update-refs` skips branches checked out in other worktrees, and Nightjar keeps one per Feature; and Azure Repos has no stacked pull requests to retarget.
- **A new Signal for a held Feature.** Rejected: it would need writing and clearing on every change of a link, and a link alone already says it.
- **Blocking links between Features.** Not now: the Tracker reads blockers of Tickets only. A Feature that waits on another says so through its Tickets' links.
