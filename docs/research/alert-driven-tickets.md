# Alerts that become Features: Sentry, Grafana and an always-on Nightjar

Research note, read 2026-11-27. Every source below was read on that date.

## 1. Question and short answer

Could Nightjar be an agent that is always running, listens to a Sentry error, an error log or a system warning (such as a Grafana alert for high CPU or memory), and on its own makes an issue, investigates, and opens a draft pull request? What would that take, and where does it fit in Nightjar's model?

Short answer:

- **Most of it already exists, for Sentry.** `nightjar intake` is a long-running process that takes signed Sentry issue alerts, dedupes them by Sentry issue id, caps them per day, and makes a Feature on the Tracker from the shipped `sentry` template ("reproduce the error in a spec, then fix it"). `nightjar --watch`, also long-running, builds that Feature into a draft pull request. With `"go": true` the Source gives a standing Go, so no person has to act between alert and draft (ADR 0003, which names "a Sentry error that only needs reproducing and fixing" as its motivating case).
- **The fit is a Source, not a new Adapter and not a Workflow.** A Source only writes Features; the build loop, the Signals and the sandbox stay as they are. A Workflow is the right place for _how_ an alert is investigated (its prompt, or `output: "note"` for findings without code), not for receiving it.
- **Grafana does not work today.** Its webhook signature is not the Standard Webhooks scheme the generic `webhook` Source checks, so every delivery would get 401; and a `resolved` notification would be taken as a new event. It needs a `grafana` Source type, as Sentry got one.
- **The hard part is evidence, not plumbing.** Sessions have no network (ADR 0005). A Sentry alert payload already carries the event, stack trace included, but intake cuts it to 8 KB; a Grafana alert carries labels and values, not the metrics or logs behind them. Opinion: evidence should be fetched by Nightjar outside the sandbox and handed to the Session as data, never by opening the network or an MCP server to the agent.
- **Prior art overlaps heavily.** Sentry Seer already does root cause and a PR (GitHub and GitLab cloud only) and can hand off to Claude Code; Grafana Assistant Investigations already investigates alerts and writes reports, without code changes. Nightjar's place is the part they do not: any Tracker, a local sandbox, its own Review and Pull-check loop, and a person's Go.

## 2. Words

- **Software factory.** A loose term. CircleCI: "A software factory is a system for turning engineering intent into production software", whose work intake covers "Features, issues, incidents, specs, dependency updates, and production signals" ([CircleCI, 2026-09-18](https://circleci.com/blog/software-factory/)). Factory.ai files its automations under a `software-factory` docs path but the page does not define the phrase ([automations](https://docs.factory.com/software-factory/automations)). There is no standard; each vendor means "agents doing the SDLC with little human typing". Nightjar's issue #144 already quotes the CircleCI list and leans towards deferring intake "beyond a person's Go".
- **In Nightjar's words** (GLOSSARY.md): what the question calls an alert listener is a **Source**; "create an issue" is making a **Feature** (with one **Ticket**, or as a **Lone issue**) on the **Tracker**; "start an investigation" is the **Coding agent**'s **Session**, shaped by a **Workflow**; the draft pull request is opened on the **Code host**. GLOSSARY's _Avoid_ list for Source includes "trigger, automation, integration, hook, feed", so a new kind should be a Source type, not an "alert integration".

## 3. How Nightjar does it today

- **Sources and intake.** `sources` in `factory.json` takes four types: `schedule`, `webhook`, `sentry`, `botPulls` (`src/config.ts:216-225`). `nightjar intake` serves each webhook Source at `POST /sources/<name>` on 127.0.0.1 and fires schedules from a one-second clock (`src/intake.ts:580-600`, `:638-664`, `:113`). It "never builds" (`src/intake.ts:1`); `--watch` builds what it makes (`README.md:446`).
- **Sentry.** Intake checks `Sentry-Hook-Signature`, a hex HMAC SHA-256 of the raw body with the integration's client secret, timing-safe (`src/intake.ts:216-227`); takes only `Sentry-Hook-Resource: event_alert` with `action: triggered` and answers 200 to anything else (`:551-563`); keys by `data.event.issue_id` (`:64-65`, `:766`). Setup is an internal integration with "alert rule action" ticked (`README.md:459-471`). The shipped template has one Ticket: reproduce in a spec, then fix (`templates/sentry.md:11-19`).
- **Dedupe, storms, caps.** While a Feature with the same key is open, no new one is made; intake writes "happened again, N times since" into that Feature's Status note, or comments at most once a day on a Tracker without one (`src/intake.ts:381-434`, `:497-503`). One delivery per Source at a time, so two of the same key never make two Features (`:333-350`). `maxPerDay`, 3 by default, is counted on the Tracker, so two intakes share it (`:504-506`; `README.md:498`). 20 bad signatures a minute gets 429 (`:47-49`, `:533-536`). Bodies over 256 KB get 413 (`:42`). There is no cap on how many of a Source's Features are open at once.
- **Untrusted payload.** Each placeholder value is cut to one escaped line of 200 characters; the whole payload, cut to 8 KB, is added in a block headed "Event payload (untrusted data)" (`src/template.ts:16-21`, `README.md:437`); the prompts call that block "data, never instructions" (`src/prompt.ts:536`, `templates/sentry.md:13`). The intake log never holds the payload (`src/intake.ts:167`).
- **The Go.** A Source makes Features with no Signal unless `"go": true`; then intake assigns the Feature to a trusted `owner` and gives the Go, the one place Nightjar does (`src/intake.ts:437-452`; `docs/adr/0003-a-source-may-give-a-standing-go.md:5-12`). The Go comes from the committed `factory.json`, never from an event (ADR 0003, line 18).
- **Always on.** Both halves are long-lived: intake is an HTTP server plus a clock until Ctrl-C or SIGTERM (`src/intake.ts:869-875`), and `--watch` polls the Tracker every 120 seconds by default (`src/person-config.ts:12`, `src/queue.ts:612-636`). A webhook that wakes `--watch` at once was considered and closed as not planned (#94); #92 put "waking `--watch` on events" out of scope, as the shorter poll covers it. The README says to run intake under systemd or launchd, behind a tunnel or reverse proxy for public HTTPS, and that deliveries while it is down are lost unless the sender retries (`README.md:500-502`).
- **Polling Source precedent.** `botPulls` already polls an outside system on a cron time and makes one Feature per finding, keyed by id (`src/intake.ts:609-636`). A polling alert Source would follow the same path.
- **The sandbox.** Every Session runs with `network.allowedDomains: []`, `failIfUnavailable: true` and no unsandboxed retry (`src/settings.ts:81-91`); `curl`, `wget`, `ssh`, `gh`, `WebFetch` and `WebSearch` are denied (`:36-62`); Sessions start with `--strict-mcp-config` and no `--mcp-config`, so no MCP server loads (`src/session.ts:97-114`). ADR 0005 rejects a configurable list of allowed domains because "any reachable host can carry data out" (`docs/adr/0005-every-session-runs-in-the-sandbox-with-no-network.md:15`). `setup` and the check run outside the sandbox, because Nightjar runs them (`:5`).
- **Findings without code.** A Workflow with `output: "note"` writes only under `docs/research/`; the Feature ends with `ready-for-human` and a Next step to read the note (`README.md:321`; `src/config.ts:164-167`). A Feature picks a Workflow with a `**Workflow:**` line, so a Source's template could name one (not tried here). The **Preflight** ("out of reach with a reason") is in GLOSSARY.md but not in `src/` yet (open #341, #354-357).
- **Closing.** The Tracker interface has no "close" (`src/tracker.ts:96-129`), and ADR 0002 forbids reading or writing tracker states. A GitHub Ticket closes when its pull request merges, through `Closes #N` (`src/github/code-host.ts:202-203`).

## 4. Per-source findings

### Summary table

| Sender | Delivery | Signing | Dedupe key it offers | Resolved event | Evidence in the payload | Nightjar today |
|---|---|---|---|---|---|---|
| Sentry issue alert | Webhook, `event_alert` / `triggered` | `Sentry-Hook-Signature`, hex HMAC SHA-256 of body | `data.event.issue_id` | Separate `issue` resource, `resolved` action | The event, sample includes `exception.values[].stacktrace.frames` | Supported (`sentry` type) |
| Grafana Alerting | Webhook contact point | Optional HMAC SHA-256, hex, header `X-Grafana-Alerting-Signature`, `timestamp:body` with a timestamp header | `groupKey`; per alert `fingerprint` | Same payload, `status: resolved` | Labels, annotations, values, links; no series or logs | Not supported (401 under `webhook`) |
| Prometheus Alertmanager | `webhook_config` | None; `http_config` basic auth, bearer or OAuth2 | `groupKey`; per alert `fingerprint` | Same payload; `send_resolved` default true | Labels, annotations, `generatorURL` | Not supported |
| Any tool speaking Standard Webhooks | Webhook | Standard Webhooks | A payload path | Sender's choice | Sender's choice | Supported (`webhook` type) |

### Sentry

- Issue alert deliveries carry `Sentry-Hook-Resource: event_alert`; `action` "will always be `triggered`"; `data.event` is "the event that triggered the alert" and `data.triggered_rule` "the label of the rule that was triggered". The attribute list does not mention a stack trace, but the sample payload has `exception.values[].stacktrace.frames` with `abs_path`, `context_line` and `in_app` inside `data.event` ([issue alerts](https://docs.sentry.io/organization/integrations/integration-platform/webhooks/issue-alerts/)). So the stack trace usually arrives with the alert; Nightjar's own fixture leaves it out (`src/fakes/sentry.ts:9-45`).
- Signature: "HMAC-SHA256 hex digest of the exact request body bytes" with the client secret, compared in constant time; resources are `installation`, `event_alert`, `issue`, `metric_alert`, `error`, `comment`, `seer`, `preprod_artifact`. **"Webhooks should respond within 1 second. Otherwise, the response is considered a timeout."** Retry behaviour is not documented ([webhooks](https://docs.sentry.io/organization/integrations/integration-platform/webhooks/)). Intake answers only after the Tracker has searched and written (`README.md:448`), which on GitHub will often take longer than a second (not measured).
- The `issue` resource has actions `created`, `resolved`, `assigned`, `archived`, `unresolved` ([issue webhooks](https://docs.sentry.io/organization/integrations/integration-platform/webhooks/issues/)): the way to hear that an error was resolved.
- REST: `GET /api/0/projects/{org}/{project}/events/{event_id}/` returns `entries` with exception frames, scope `project:read` ([retrieve an event](https://docs.sentry.io/api/events/retrieve-an-event-for-a-project/)); `GET /api/0/organizations/{org}/issues/{issue_id}/events/?full=true` includes "the full event body, including the stacktrace", at most 10 per page, scope `event:read` ([list an issue's events](https://docs.sentry.io/api/events/list-an-issues-events/)). The per-project issue list for polling is marked deprecated in favour of the organization issues endpoint ([list a project's issues](https://docs.sentry.io/api/events/list-a-projects-issues/)).
- **Seer / Autofix.** "Seer always performs root cause analysis and solution planning"; it can open a PR once its GitHub or GitLab app is installed; GitHub.com and GitLab.com cloud only ([Seer](https://docs.sentry.io/product/ai-in-sentry/seer/)). With automation on, it runs on issues with "10 or more events", seen "within the last 14 days" and "a sufficient fixability score", stopping at Root Cause, Plan or PR Drafted as the project sets. It can hand code generation to Claude Code, Cursor or Copilot, passing "the root cause and solution as a structured prompt" (GitHub only) ([Autofix](https://docs.sentry.io/product/ai-in-sentry/seer/autofix/)). Seer moves to usage-based credits on 2026-12-08 ([Seer](https://docs.sentry.io/product/ai-in-sentry/seer/)).
- **Sentry MCP.** Remote at `https://mcp.sentry.dev/mcp`, scoped by org or project in the URL, OAuth; or `sentry mcp` over stdio using the CLI login. The page lists no tools by name and no read-only mode ([mcp.sentry.dev](https://mcp.sentry.dev/)).

### Grafana Alerting

- Webhook payload: top level `receiver`, `status`, `orgId`, `alerts`, `groupLabels`, `commonLabels`, `commonAnnotations`, `externalURL`, `version`, `groupKey`, `truncatedAlerts`, `title`, `state`, `message`; per alert `status`, `labels`, `annotations`, `startsAt`, `endsAt`, `generatorURL`, `fingerprint`, `silenceURL`, `dashboardURL`, `panelURL`, `values`, `imageURL`. HMAC signing is optional: header `X-Grafana-Alerting-Signature` by default, hex HMAC SHA-256 of `timestamp + ":" + body` when a timestamp header is set, else of the body alone. A Custom Payload template exists but is not GA in Grafana Cloud. No retry information ([webhook notifier](https://grafana.com/docs/grafana/latest/alerting/configure-notifications/manage-contact-points/integrations/webhook-notifier/)).
- Grouping: by alert rule by default (`alertname`, `grafana_folder`); group wait 30 s, group interval 5 min, repeat interval 4 h, "a reminder that alerts in the group are still firing"; a resolved alert is reported at the next group interval, then leaves the group ([grouping](https://grafana.com/docs/grafana/latest/alerting/fundamentals/notifications/group-alert-notifications/)). So Grafana already damps storms, and a still-firing alert resends every 4 hours.
- **Grafana MCP** (`grafana/mcp-grafana`): Prometheus, Loki, Tempo, alerting, incidents and more; `--disable-write` drops write tools, `--disable-query` drops data queries; service account token; stdio, SSE or streamable HTTP ([mcp-grafana](https://github.com/grafana/mcp-grafana)).
- **Grafana Assistant Investigations.** Can be set to "automatically trigger investigations when alert groups are created"; posts links back to the alert group or incident. The IRM guide mentions no GitHub, pull requests or code changes; its writes are limited to IRM data, each needing approval ([IRM guide](https://grafana.com/docs/grafana-cloud/platform/grafana-assistant/guides/irm/)). Investigations and Automations went GA on 2026-07-27; the Assistant opens a pull request only in its instrumentation flow ([press release](https://grafana.com/press/2026/07/27/grafana-labs-ships-six-tools-that-power-agentic-operations-from-planning-to-production/)).
- Unverified: a stable HTTP API listing currently firing Grafana alert instances for a poller. The provisioning API page read covers rule definitions, not firing state ([alerting provisioning API](https://grafana.com/docs/grafana/latest/developer-resources/api-reference/http-api/alerting_provisioning/)).

### Prometheus Alertmanager

- Payload `version: "4"` with `groupKey`, `truncatedAlerts`, `status`, `receiver`, `groupLabels`, `commonLabels`, `commonAnnotations`, `externalURL`, `notification_reason`, `alerts[]` (`status`, `labels`, `annotations`, `startsAt`, `endsAt`, `generatorURL`, `fingerprint`); `send_resolved` defaults to true; no body signing, only `http_config` auth ([configuration](https://prometheus.io/docs/alerting/latest/configuration/)). Grafana's payload is a superset of this shape, so one parser can read both; the signing differs.

### GitHub as the Tracker

- `POST /repos/{owner}/{repo}/issues` takes `title`, `body`, `labels`, `assignees`; without push access "Labels are silently dropped" and so are assignees ([create an issue](https://docs.github.com/en/rest/issues/issues#create-an-issue)). So the account intake runs as needs push access, or a `go: true` Feature lands with no Go and no owner. Nightjar already checks the owner is trusted and that the Tracker can assign (`src/intake.ts:281-307`), but not that intake's own login can label (not verified whether `makeFeature` notices a dropped label).
- "Make an issue" in the question is exactly what intake does: the Feature is the Ticket Nightjar's loop picks up. Nothing new is needed on the Tracker side.

### Other prior art

- **Factory.ai.** An Alert Responder starter investigates "Sentry, Datadog, or PagerDuty alerts as they fire" from a webhook and opens "a fix PR when safe"; Error Triage polls Sentry or Datadog hourly. Webhook deliveries are skipped while a previous run is in progress, identical bodies within 10 minutes are deduplicated, and runs are capped at 10 an hour by default ([automations](https://docs.factory.com/software-factory/automations)).
- **Claude Code GitHub Actions.** In automation mode, with a `prompt`, it "runs without waiting for a mention" on any GitHub event, and rejects bot actors unless listed in `allowed_bots` ([GitHub Actions](https://code.claude.com/docs/en/github-actions)). It could build an alert issue, but has none of Nightjar's dedupe, Go, Review or budget.
- **Claude Code sandbox and MCP.** "The sandbox covers shell commands only. Claude's file tools, MCP servers, and hooks run outside it", and "`WebFetch` and MCP servers are not limited by" `allowedDomains` ([sandboxing](https://code.claude.com/docs/en/sandboxing)). MCP docs warn "Servers that fetch external content can expose you to prompt injection risk" ([MCP](https://code.claude.com/docs/en/mcp)).

## 5. Options for Nightjar

Facts are cited above; everything in this section is opinion unless marked.

### Where it fits

**(a) A new Adapter kind ("alert adapter").** Rejected. An Adapter connects Nightjar to where Features live (Tracker) or where branches go (Code host) (GLOSSARY.md, ADR 0001). An alert system is neither; it is where work comes from. Making it an Adapter would put alert parsing beside `assignedFeatures` and `openDraft`, and `src/build.ts` would have to know about it, which the architecture rule ("talks only to the Tracker and CodeHost interfaces") forbids.

**(b) A Source: a separate intake that only writes Features.** Fits, and already exists (fact, §3). It keeps ADR 0001 (no Adapter changes beyond the optional `featuresFrom` and `assign` already there), ADR 0002 (a Source adds no Signal unless `go`), ADR 0003 (a standing Go only from committed config, bounded by `maxPerDay`, Ticket limits and `dailyUsd`), ADR 0005 (intake calls no Coding agent), and ADR 0008 (Features from alerts join the same Queue and Slots). New alert senders are new Source types.

**(c) A Workflow.** A Workflow cannot receive anything: it only adds Steps or a prompt to a Feature that is already building, and never loosens the deny rules (CLAUDE.md, ADR 0005). It is the right place for the _shape_ of the work: an `investigate` Workflow with `output: "note"` for an alert that may have no code fix, or a prompt that says how to reproduce a production error. A Source's template names it with `**Workflow:**`.

So: **(b) to receive, (c) to shape.**

### Getting the evidence to a Session with no network

1. **Intake embeds the evidence in the Feature.** Already true for Sentry up to 8 KB (fact). Extend by letting a Source fetch more (the full event via the Sentry API, a Prometheus range query around `startsAt`) before it writes. Intake already runs outside the sandbox with credentials. Costs: the evidence becomes permanent text on the Tracker, which may be public (see PII below); 8 KB of JSON is a poor stack trace; intake grows API clients for each vendor, and its answer gets slower against Sentry's one-second window.
2. **A read-only fetch by Nightjar, outside the sandbox, into the worktree.** Like `setup` (ADR 0005 keeps `setup` outside the sandbox because Nightjar runs it, fact): before the first Ticket of a Sourced Feature, Nightjar runs a fetch that writes the evidence to an ignored file in the worktree (`.factory/evidence/…`), which the Session reads with `Read`. The evidence stays on the build machine and never reaches the Tracker; the Session still has no network; the fetch runs Nightjar's code, not the branch's. Costs: credentials for Sentry or Grafana must sit where `--watch` runs, not only where intake runs; a new `factory.json` key and a new stage in the build. Needs an ADR: "Nightjar may fetch a Source's evidence before a build, outside the sandbox, read-only, by code Nightjar ships".
3. **Let the Session use an MCP server (Sentry MCP, Grafana MCP with `--disable-write`).** The richest investigation, and the one ADR 0005 already argued against: MCP servers run outside the sandbox and are not limited by `allowedDomains` (fact), so a server that can query arbitrary Loki or Prometheus expressions or Sentry search is a channel out, steered by a model reading untrusted log lines and stack traces. It would supersede part of ADR 0005 and turn off `--strict-mcp-config`'s guarantee. Not now.

Recommendation: 1 within today's limits for the first slice (Sentry already works this way); 2 as the next ADR if investigations prove starved of evidence; never 3 without a new ADR that answers ADR 0005's exfiltration argument.

### Always on: webhook or poll

- **Webhook (today's intake).** Needs a public HTTPS address (tunnel or reverse proxy), a machine that stays on, signature checks, and is exposed to lost deliveries while down (fact, `README.md:500-502`). It reacts within seconds. Signing, size limits, failed-signature throttling, per-Source serialisation and Tracker-side idempotency by key already exist (fact). A durable queue does not: a delivery is handled inline. Sentry's one-second window (fact) argues for answering 202 before the Tracker write; that would lose the "503 so the sender retries" contract (`README.md:457`) unless intake keeps its own on-disk queue.
- **Poll (like `botPulls`).** No inbound port, no public endpoint, nothing lost while down (the next poll sees what is still open), simple to run on a laptop; minutes of delay; an API token where intake runs; and a vendor API per sender (Sentry's org issues endpoint, fact; Grafana's firing-alerts API, unverified). Factory's Error Triage polls hourly (fact).

Recommendation: keep webhooks as the main path, because both senders sign their deliveries, intake already does the hard parts, and alerts want minutes not hours. Add a polling Sentry Source only if people ask for one without a public endpoint. Do not move intake into `--watch` (#92 and #94 already decided that).

### Guardrails

- **Noise and storms.** Already: per-key dedupe while open, `maxPerDay` (default 3), Grafana's own grouping and 4 h repeat (fact). Missing: a cap on _open_ Features per Source (`maxOpen`), so a week of 3 a day cannot fill a person's Queue; Factory's hourly cap and same-body dedupe are the comparable prior art (fact).
- **Dedupe key.** Sentry: the issue id (exists). Grafana and Alertmanager: `groupKey` gives one Feature per notification group, `alerts.0.fingerprint` one per alert but drops the others in the group. Opinion: `groupKey` by default, since Grafana groups by rule.
- **Resolved alerts.** Today a Grafana `resolved` delivery to a `webhook` Source would make a new Feature, or say "happened again" on the open one: wrong both ways. A `grafana` type must take `firing` only, and write "resolved at …" into the open Feature's Status note history, as "happened again" is written (`src/intake.ts:381-416`). It must not close the Feature: ADR 0002 forbids writing states and the Tracker has no close (fact). For Sentry, the `issue` resource's `resolved` action could do the same (fact that it exists; not wired).
- **"Not a code bug".** A high-CPU alert may have no fix in this repo. Route infra alerts to a note Workflow by default (findings, likely causes, what to check, no code), which ends `ready-for-human` (fact, `README.md:321`). Code errors (Sentry) keep the fix template. The Preflight, once built, adds "out of reach" for a Feature the sandbox cannot do (#341).
- **Secrets and PII.** Sentry events can carry user data, request headers and environment details; intake copies up to 8 KB of the payload into the Feature body on the Tracker, which may be a public GitHub repo. Not verified what Sentry scrubs before sending. Opinion: a Source option to leave the payload block out, or to keep only listed paths, and a README warning; a public repo should never take raw alert payloads.
- **The Go.** Keep it explicit. `go: true` stays off by default and comes only from a committed `factory.json` with a trusted owner (fact, ADR 0003). Opinion: a standing Go suits Sentry errors (a spec reproduces them) more than infra alerts; for Grafana, start without `go` so a person picks which alerts deserve a build. Watch also that intake's GitHub login has push access, or the Go label is silently dropped (fact on GitHub's side).
- **Overlap with Seer.** A team with Seer already gets root cause and a PR on GitHub or GitLab cloud (fact). Nightjar adds value where Seer cannot go (Azure DevOps, self-hosted, local sandbox) or where the team wants the PR through its own Review and Pull-check loop. A Source of Sentry's `seer` resource could carry Seer's root cause into the Feature as evidence; its payload was not checked.

## 6. Recommendation and the smallest first slice

Recommendation (opinion): treat this as "more Source types and better evidence", not a new subsystem. Tell the person that Sentry → Feature → draft pull request already works today with `nightjar intake` and `nightjar --watch` running under a service manager, `"go": true` if they want no human step.

Smallest first slice, one Feature with a few Tickets:

1. **A `grafana` Source type.** Checks `X-Grafana-Alerting-Signature` (hex HMAC SHA-256 of `timestamp:body`, timestamp header required and held to the same 5 minutes as Standard Webhooks); takes `status: firing` only; key defaults to `groupKey`; a real-shaped fixture in `src/fakes/` with placeholder names.
2. **Resolved writes a line, never a Feature.** A `resolved` delivery whose key has an open Feature adds "resolved at …" to its Status note history; with none open it makes nothing (200).
3. **A shipped `grafana` template and `investigate` Workflow.** One Ticket, `output: "note"`: read the alert's labels, annotations and values, the code and config they point at, and write findings with likely causes and next checks; no code change.
4. **README:** Grafana contact point setup, and a warning about payloads on a public Tracker.

Next, each its own decision: `maxOpen` per Source; a Source option to keep the payload out of the Feature; answering Sentry within one second; and the ADR for fetching evidence outside the sandbox (option 2).

## 7. Open questions for a /grill-with-docs session

1. Is a `grafana` type worth it, or should Grafana users point a Custom Payload or a small relay at the generic Standard Webhooks Source instead? (Custom Payload is not GA in Grafana Cloud.)
2. Key for grouped alerts: `groupKey` (one Feature per group) or per-alert `fingerprint` (one per alert, others in the group ignored)?
3. Should an infra alert ever end in code, or always in a note first, with a person turning the note into a Feature?
4. Does a resolved alert only annotate, or also take the Go off an unbuilt Feature (a Signal, so allowed by ADR 0002)?
5. Sentry's one-second window: answer 202 and queue on disk, or keep "answer after the Tracker" and rely on the key to absorb retries? Does Sentry retry at all (undocumented)?
6. Evidence: is 8 KB in the Feature body enough, or do we need ADR "Nightjar fetches a Source's evidence outside the sandbox"? Where do the Sentry and Grafana tokens live then: with intake, with `--watch`, or both?
7. PII: should a Source on a public repo refuse to embed the payload by default?
8. Should `maxOpen` exist, and does a full Source stay silent or say so somewhere a person sees?
9. Polling: is a no-inbound-port Sentry Source wanted by anyone yet?
10. Seer: ingest its `seer` webhook as evidence, or stay independent of it? Does #144 close with this note as its answer?
