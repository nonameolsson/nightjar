# Architecture

The module map of Nightjar. Words are in [GLOSSARY.md](../GLOSSARY.md); decisions in [docs/adr/](adr/).

- `src/build.ts` is the build loop: one Feature from the Go to a draft pull request. It talks only to the `Tracker` (`src/tracker.ts`) and `CodeHost` (`src/code-host.ts`) interfaces, starts every Session through `codingAgent` (`src/coding-agent.ts`) and branches only on its outcomes, and speaks of Signals (`src/signals.ts`), never label names.
- `src/feedback-round.ts` is the Feedback round, which `build.ts` runs after the Steps and before the review when the Code host has `feedback` and `reply`, the Feature's branch has an open pull request, and that pull request has trusted feedback that no `Factory-Feedback` trailer on the branch names (`answeredFeedback`). Untrusted feedback is dropped there and never reaches the Coding agent. One new Session gets that feedback and the Feature's diff, cut at `DIFF_CHARS` as a Step's is. It runs on a Ticket's budget and minutes, then the check with the usual fix rounds in the same Session. It lands as one commit (`commitFeedback`) whose trailer names only the feedback the Session says it answered. After the push, `build.ts` replies to each answered piece with the commit's short id, and the Code host adds the footer that keeps the reply from coming back as feedback. A round that stays red, reports itself blocked, answers nothing or changes no file is thrown away onto the `-attempt-feedback` side branch. The Feature then gets needs info and a comment naming each piece left unanswered and why, and the run goes on. The ledger records the round and its fix rounds as step `feedback`. The status file, the live view and `nightjar ui` show it as `Feedback round`. The pull request body gets a Feedback section with the branch's rounds and their cost, counted from the ledger (`feedbackRounds`), and what this run left unanswered.
- `src/review-round.ts` is the Review round, which `build.ts` runs after the Review and before the push while the Review says `changes`, the Feature is complete (every Ticket built, the check green, the run not paused) and the build has had fewer than `review.fixRounds` rounds (default 2, from `DEFAULT_REVIEW_FIX_ROUNDS`; counted per build, so a new Go gives them again); the Review then runs again. The round's answer says per issue, by its number, fixed or declined with a reason; the loop keeps the declined ones for the build (a local of `reviewRounds`, so a new Go starts with none) and hands them to each later Review's request. A round that declines every issue needs no commit and is not failed. It runs wherever the Review runs, after a Feedback round and on a note Feature too, never after a Pull-check fix. A round first checks the day's spend, which pauses it as it pauses any Session. One new Session gets the last Review's issues and the Feature's diff, cut at `DIFF_CHARS` as a Step's is; it runs on a Ticket's budget and minutes and on the Review's model and effort. Then the check with the usual fix rounds in the same Session, and one commit (`commitReview`) with a `Factory-Review` trailer naming its round. A round that stays red, reports itself blocked or fixes an issue yet changes no file is thrown away onto the `-attempt-review` side branch, and no more rounds run; one the Session pauses or a person stops is thrown away too. The ledger records the round and its fix rounds as step `reviewRound`, and the status file, the live view and `nightjar ui` show it as `Review round`, round N of `fixRounds`. The pull request body's Review section (`src/review-section.ts`, from the `ReviewStep`s `build.ts` collects: each Review, each round with its outcome and cost summed from the round's ledger rows, in order, then the issues of the last Review still open, then the issues the rounds declined, with their reasons) and its `Review rounds` cost line count the rounds as their own kind of work; the comment carries only the last Review.
- `src/github/` holds the GitHub adapters, the only code that calls `gh` (a lint rule holds this). Its Code host's `nightjarDrafts` reads the Pull checks from the head commit's check runs and commit statuses, with an Actions job's workflow, failed step and log tail (each job read once per process), and counts a review or comment by any login but the signed-in one as a person engaging. Its `openPulls` lists every open pull request from the repo's own branches with the prefix, with the pull request's commits (dated by their committer) and its reviews in `CHANGES_REQUESTED`, each trusted by the feedback rule. `src/fakes/` holds the in-memory Tracker and Code host the build loop's specs run over; those specs fake the Coding agent with outcomes.
- `src/conflicts-section.ts` is the Conflicts section of a draft's body: after `build.ts` opens a draft or updates its body (a Pull-check fix round too), it asks the Code host's optional `conflicts` (yes, no or unknown; the GitHub adapter reads `mergeable`, the Azure Repos adapter `mergeStatus`), asking again every second for about ten seconds while it is unknown. A draft that conflicts gets a `## Conflicts with <base>` section; one that does not, or stays unknown, has none, and an earlier run's is dropped. It sets no Signal and writes no Tracker comment, and `--watch` does not check open drafts for it.
- `src/footer.ts` is the footer every comment and reply of Nightjar ends with, and the one test that tells its words from a person's: a Code host's `feedback` leaves out whatever ends with it. `src/github/trust.ts` is the one trust rule of the GitHub Tracker's comments and the GitHub Code host's feedback; `src/check-output.ts` cuts a failed check's output to its last 4 KB.
- `src/azure-devops/` holds the Azure DevOps adapters, the only code that calls Azure DevOps: `sign-in.ts` (the `az` token, else `AZURE_DEVOPS_EXT_PAT`), `api.ts` (the one signed-in HTTP layer, with a request seam), `index.ts` (`openAzureDevOps`, one API every Azure DevOps adapter shares), `tracker.ts` (Boards), `code-host.ts` (Azure Repos; it links work items when `src/adapters.ts` pairs it with Boards of the same organization, else names Tickets in the body; its `nightjarDrafts` reads the Pull checks from the statuses on the head push and the build validation policies, with a failed build's job, failed step and log tail from its Pipelines timeline (each build read once per process), and counts a comment that is not Azure Repos' own, or a vote, by any identity but the signed-in one as a person engaging; its `feedback` reads the comments a person typed in each thread (a system thread is skipped), a vote of Waiting for author or Rejected as a review (Azure Repos notes each vote in a `VoteUpdate` thread, which gives it its id and time), and a failed status of the head push as a check, trusted by genre or name (`codeHost.trustedChecks`, else Azure Pipelines); its `reply` answers a comment in its own thread, and a review or check in a new comment that quotes it; its `openPulls` lists the active pull requests of the prefix's branches with their commits (a message Azure Repos cuts short is read whole from the commit) and the Waiting for author votes as changes requested), `trust.ts`, the one trust rule of the Boards Tracker's comments and the Azure Repos feedback (the `trusted` list, else the project's Contributors group), and `fake-azure-devops.ts`, the in-memory Azure DevOps its specs run the real adapters over.
- `src/config.ts` loads and validates `factory.json`; `src/person-config.ts` the person's own optional `~/.config/nightjar/config.json` (`dailyUsd`, `assignee`), found through the injected env; `src/adapters.ts` builds the adapters `factory.json` names. `src/adapter-module.ts` loads a repo's own adapter from a `type: "module"` entry and refuses one that lacks an export or a method (`docs/custom-adapters.md`).
- `src/contract/` is the Adapter contract suite (`feature-writer.ts` is the creation suite, run over a Tracker that also implements the optional `FeatureWriter`; `waiting-on.ts` the suite for the optional `waitingOn`, `sources.ts` the one for the optional `featuresFrom`, `assign.ts` the one for the optional `assign` and `trusts`; `ticket-counts.ts` the suite for the optional `ticketCounts`; `shelf.ts` the suite for the optional `shelf`, a person's Shelf (ADR 0009); `nightjar-drafts.ts` the suite for the Code host's optional `nightjarDrafts`, whose harness also hands it the `DraftsWorld` that plays a pull request's Pull checks and a person's actions; `feedback.ts` the suite for a Code host's optional `feedback` and `reply`; `open-pulls.ts` the suite for its optional `openPulls`, whose harness gives the drafts world, the bench, and `commit(message)`; `publish.ts` the suite for its optional `publish`, which reads `draft` from the harness's `pull`); `run.ts` runs it without a test runner and `command.ts` is `nightjar contract MODULE` (the module exports `trackerHarness` and/or `codeHostHarness`).
- `src/main.ts` is the command (`src/cli.ts` runs it); `runNightjar(argv, host)` takes the `Os` (platform and kernel, from `src/sandbox.ts`; only `src/cli.ts` reads the real one), env, cwd, and init's `ask` and `prompter` from a `Host`, which specs inject. It stops every command on `win32` first. `src/queue.ts` picks the next Feature for `--once` and `--watch`, and holds the revisit pass (ADR 0004): with `pullChecks.enabled` in `factory.json` and a Code host that has `nightjarDrafts`, `--watch` first takes the oldest of Nightjar's draft pull requests whose Pull checks finished red, that no person engaged with, whose body's Feature marker names a Feature assigned to the person holding no Signal, and hands it to `fixPullChecks` in `src/build.ts`, once per head commit in a run; it does so before each Queue pick and on each idle tick. When no Feature has the Go and the Code host has `openPulls`, `feedback` and `reply`, the Queue takes a Feature assigned to the person, with no Go, working or needs info, whose open pull request on the branch its title names (`openPulls('factory/')`, matched by the body's Feature marker) has a trusted request for changes later than its last `Factory-Feedback` commit (`newRequest` in `src/feedback-round.ts`), and builds it with `buildFeature(…, { asked })`, so its Feedback round's commit carries a `Factory-Feedback-Asked` trailer naming the request; a pull request is taken once per request in a run. Those trailers count its automatic rounds: at 5 (`AUTOMATIC_ROUNDS`), a new request gets the Feature needs a person and a comment instead, unless it carries needs a person already. `dryRun` (doctor and init) lists such Features as `would answer feedback on #N`. `fixPullChecks` is an entry beside the build loop, not inside it: it opens the worktree at the remote branch, leaves the pull request alone unless the head commit carries a `Factory-` trailer, resumes the head commit's `Factory-Session` with the failed Pull checks in the gate report's shape (`pullChecksReport` in `src/gate.ts`), runs the repo's check with the usual fix rounds, and pushes a green fix as a new commit with a `Factory-Pull-Fix` trailer; a red one is kept on an attempt branch. No review and no Step runs after it. Each round is capped by `pullChecks.fixUsd` and `fixMinutes` (`pullFixLimits`); a round that gives up, or a pull request red again after `fixRounds` rounds (counted from the branch's trailers), gets the Feature needs a person, a comment, and a hidden mark in the pull request body that keeps the pass off it. The Feature holds `working` for the round, and every round that ran, a given-up one too, adds a block (summary, failing Pull checks, cost) to the body's Pull checks section (`src/pull-checks-section.ts`); the ledger records the round's Sessions, its check's fix rounds too, as step `pullChecks`, and the status file, the live view and `nightjar ui` show it as `Pull-check fix`, round N of `fixRounds`. `src/publish.ts` holds what Publish (ADR 0006) reads of a pull request: the hidden mark the build loop writes into every body it makes, whether the Feature was complete and the last Review approved (`publishMark`, read back by `publishMarkOf`), so the pull request, not a Signal, is the record; the Code host's optional `publish` takes a draft out of draft, and `nightjar doctor` warns when `publish` is on and the Code host lacks it or `nightjarDrafts`. The Publish pass is the revisit pass's other half (`publishPass` in `src/queue.ts`, on when `factory.json` sets `publish` and the Code host has `publish` and `nightjarDrafts`, whether or not `pullChecks.enabled` is on): under `--watch` only, before each Queue pick and on each idle tick, it publishes the oldest of Nightjar's drafts for which `readyToPublish` holds: the mark says complete and approved, no person engaged (`personEngaged`) or pushed (every commit of the branch carries a `Factory-` trailer), and the Pull checks finished green, where a head commit with no checks counts as green once `NO_CHECKS_WAIT_MS` (10 minutes) have passed since `openedAt`; a Code host that does not say `openedAt`, `checkCount` and `commits` on its drafts never has one published. Nothing publishes under `--once` or when the draft opens, a pull request is published once, and none is turned back into a draft. After it publishes, the pass writes the hidden `nightjar-published` mark into the body (`markPublished`), and `nightjarDrafts` lists a pull request out of draft only when it carries that mark, so the Pull-check pass still fixes a pull request Nightjar published until a person engages, while one a person marked ready stays theirs. `dryRun` lists a draft it would publish as `would publish #N`. `src/doctor-feature.ts` is `nightjar doctor FEATURE`: it reads a Feature's open Tickets through the Tracker and checks each against `src/ticket-contract.ts` and the Tickets against each other in `src/feature-faults.ts` (a pure function), running no machine check and writing nothing.
- `src/checks.ts` lists the checks in order (API key, Node, the sandbox (`src/sandbox.ts` asks the machine: Seatbelt on macOS; on Linux and WSL2, not WSL1, bubblewrap and socat, and a trial bwrap sandbox that AppArmor may refuse), checkout, `factory.json`, Tracker and Code host logins, a warning for each install command in `allowedCommands` (`src/install-commands.ts`; a Session has no network to fetch with, so it belongs in `setup`), `claude` installed and signed in, commit signing, each Workflow's skills), each naming the facts it needs from the ones before it; `src/check-runner.ts` runs them into lines, skipping a check whose need is missing, and `checkMachine` turns what they found into `Ready` or a refusal. The fix a Tracker or Code host failure needs (`gh auth login`) comes from its adapter, as `Adapters.trackerFix` and `codeHostFix`. A build stops at the first failure, `src/doctor.ts` (`nightjar doctor`, alias `--dry-run`) runs all and lists them, and `src/init.ts` (`nightjar init`, select prompts on a terminal through `src/prompter.ts`, else answers on stdin through `src/ask.ts`) shows what it is about to do and asks to go on, then writes `factory.json`, calls `Adapters.prepareSignals` (`src/github/labels.ts` creates the labels) and then runs the same checks.
- `src/create.ts` is `nightjar create FILE`: `src/feature-file.ts` reads a Feature file in the shape of `docs/ticket-contract.md` (checking each Ticket through `src/ticket-contract.ts`, the same check `ticketFaults` runs on a Ticket's body), and the configured Tracker makes it through `FeatureWriter`. `skills/nightjar-feature/` is the Claude Code skill the package ships, which writes that file.
- `src/template.ts` is a Source's template (`sources` in `factory.json`, read by `src/config.ts`): it fills a Feature file from an untrusted payload (plain placeholders, each value cut to one escaped line, the payload cut to 8 KB in a fenced block), adds the `**Source:**` line and the hidden marker `<!-- nightjar:source=NAME key=KEY -->`, and reads the marker back; `templates/` holds the templates Nightjar ships. The Tracker finds the Features of a Source with its optional `featuresFrom` (`sourcedFrom` in `src/tracker.ts` keeps those whose first marker names the Source). `src/checks.ts` lists each Source in `nightjar doctor`; a Source's fault stops no build.
- `src/intake.ts` is `nightjar intake [--port PORT] [--host HOST]` (its arguments in `src/args.ts`): a `node:http` server, on 127.0.0.1 unless `--host` says otherwise, with one path per webhook Source, `/sources/<name>`. It checks the Standard Webhooks signature and timestamp (for a `sentry` Source, `Sentry-Hook-Signature` instead, and it takes the `event_alert` resource only, keyed by the issue id unless `key` says otherwise; `src/fakes/sentry.ts` holds a real-shaped alert with placeholder names), asks `featuresFrom` for an open Feature with the event's key and for the day's count, and makes the Feature through `FeatureWriter` (`makeFeature` in `src/create.ts`) or, on the open one, writes "happened again" into the history of its Status note (`readStatusNote` and `withEarlier` in `src/status-note.ts`; a Tracker without `statusNote` gets a comment at most once a day instead). It answers only after the Tracker has, with the codes the README lists, and logs each delivery to `.factory/intake.log` without its payload. It also fires each `schedule` Source at its due time (a clock read each second, so a spec calls `tick` over an injected clock) through the same path, with no payload and the Source's name as its key; times missed while it was down or asleep make one Feature at most. At each due time of a `botPulls` Source it reads the Code host's optional `botPulls` (the open pull requests of the repo's own branches under the Source's prefixes, a fork's left out) and, through the same path, makes one Feature for each whose Pull checks finished red with a check that ran (`checksToFix`; one with no job, step or log never started), keyed by the pull request's id, its payload the bot's title, branch, link and failed checks, never its body. It adds the `**Base:**` line and the bot pull request's hidden mark (`src/base-line.ts`); a pull request whose Feature is open is passed over without a log line. A Code host without `botPulls` keeps such a Source from starting. `src/cron.ts` is the cron reader (five fields, `@daily`, `@weekly`, the machine's local time zone; `src/config.ts` refuses a bad time when `factory.json` loads, `src/checks.ts` prints each schedule's next due time). For a `go: true` Source it then assigns the Feature to the owner (`assign`) and gives it the Go, the one place Nightjar gives the Go (docs/adr/0003); `goFault` there is the check, shared with `doctor`, that the Tracker can assign and trusts the owner. It never builds, calls the Code host only for `botPulls`, and never the Coding agent; a Tracker without `FeatureWriter` or `featuresFrom` keeps it from starting, as does an untrusted owner or a Tracker without `assign` for a `go: true` Source.
- `src/base-line.ts` reads and writes a Feature's `**Base:**` line and the hidden mark of a bot pull request. `buildFeature` and `fixPullChecks` in `src/build.ts` open the worktree on the line's branch instead of the base branch (a name git could misread gets the Feature needs info), the draft still opens against the base branch, and when a draft opens for a Feature with the mark, `build.ts` comments once on the bot's pull request with a link to it; it never pushes to that branch or closes that pull request.
- `src/workflow.ts` is the Workflow module: it picks a Feature's Workflow (its `**Workflow:**` line, else `defaultWorkflow`), and its `WorkflowRun` runs the Steps at a point (after each Ticket, or after all of them before the review) and keeps their reports for the pull request's section. It owns a Step's rounds, `until`, budget, serve command, and its end: its own commit with a `Factory-Step` trailer, or thrown away. `build.ts` calls it at those two points and branches only on whether the run goes on, pauses or stops; it lends the Steps its fix rounds, ledger and status file. `serve.ts` starts a Workflow's serve command, `skills.ts` lists the skills a headless session loads (`checks.ts` checks each Step's `/skill` against them, per Workflow), and `settings.ts` adds a Workflow's commands, tools and localhost network to its Steps without touching the deny rules.
- `src/coding-agent.ts` is the Coding agent module: `codingAgent(setup, session)` starts a Session for a Ticket's build, a fix round, a Step round, a Feedback round, the review, a Review round or a Retro, and says how it ended (`failed`, `paused` and `aborted` for every kind, besides the kind's own answer). It owns each kind's prompt, schema, tools, settings and model and effort (a CLI flag, then the work's own setting, then the repo's defaults); the deny rules stay in `settings.ts`, and the questions comment in `prompt.ts`.
- `src/spend.ts` is the Spend module, in `Deps`: it records each Session's cost as a ledger `Entry` and answers `dayOver(now, dailyUsd)` (the pause's words) and `allowance(cap, spent)` (what a piece of work may still spend, and whether that is enough for another Session); the cap arithmetic lives there alone. Its adapters are the file, `fileSpend` in `src/ledger.ts` (`.factory/runs.jsonl`, whose format and `ledgerPath` stay there), and `memorySpend` in `src/fakes/spend.ts`, which the build specs assert over; `src/spend.spec.ts` is the one contract spec both run. `StatusFile` reads the day's spend through it. `status-reader.ts` and `ui.ts` read the file's lines for the live views.
- `src/build-cost.ts` splits a build's ledger lines by stage of the build loop (`STAGES`: Tickets, Steps, Review, Review rounds, Pull checks, Feedback, with room for a stage before the Tickets) and by model (`byModel`, each model's tokens and dollars summed, the dearest first). A fix round goes with the work whose Session it resumes, so a Step's fix rounds after a Ticket count under Steps; lines with no `models` (older lines) are counted apart as `unrecorded`. `status-reader.ts` gives each Completed build and the build in flight its split (`buildCost` over `linesOnFeature` in `ledger.ts`, the same lines as its dollars; a Pull-check fix round's line, which falls after the `pull` event as the round runs later and writes no event, goes with the Feature's latest `pull` event at or before it), and `nightjar ui` folds it under the cost on a Completed card, a Table row and Building now (a `<details>` keyed by place and build, kept open and focused across a live swap). The pull request's Cost section reads the run's own costs instead: each Step after all Tickets on a line of its own with its rounds (a round's fix rounds count in it; `StepRound` tags them), then `### By model` when any Session named its models, with what the others cost.
- `src/build-stages.ts` says how each stage of a build went, for the Steps bar (`buildStages`, a pure function over the build's ledger lines, the same lines as its cost, so the Logbook can use it too): passed; passed after a retry or a round (a passing failure, a pause or a stop by a person tried again, a fix round, a `round 2` or later in the outcome, or a second Review, Review round, Feedback round or Pull-check fix); failed (a `failure` other than passing, an outcome that failed, gave up, was blocked or asked questions, or a passing failure, pause or stop that nothing tried again); running (`runningStage` of `status.json`'s step); and, for a stage with no line, not needed when `factory.json` never runs it (`neverRun`: the build's Workflow has no Steps, or no Workflow has any when its Logbook names none, the Review off or with no rounds, Pull checks off), the build went past it in time (a Feedback round runs after the Steps and before the Review) or ended with a pull request, else not reached. `status-reader.ts` reads `factory.json` for `neverRun` (none when it is missing or does not load), with the Workflow of the Feature's last `buildStarted` Logbook entry up to the build's end and gives each Completed build and the build in flight its stages; `nightjar ui` draws them as a row of segments beside the Eggs on every Board card and Table row with a build to show (a card that is active again shows its last run's), with a legend above the Board and the Table.
- `src/last-week.ts` counts the last seven local days for the Overview (`lastWeek`, a pure function; `weekOf(now)` is the span, from local midnight six days back up to the next local midnight, as `Spend.today` counts a day): the dollars of the ledger's Sessions in it, the Features whose latest finished run in it was a draft pull request (completed) or a failure (failed), and the Features with a hand-back in it that did not fail (handed to a person; a failed Feature is handed back too and counts as failed alone). `readFactory` gives it the ledger, the `pull` and `failed` events of status.json's `recent` (the last ten events only) and `handedBack`, and puts the result on `FactoryView.week`, which a hand-made view lacks and the page draws as zeros. The Overview opens with it (`week` in `ui.ts`): each count of Features is a link (`data-goto`) that the page script turns into the Table's outcome filter, which shows every row with that outcome of any day (or waiting now), not the week's, as the link and a note under the counts say (`any`, `completed`, `failed`, `waiting` for needs a person, kept with the sort and state chips in local storage as `nightjar-table`) and focuses it.
- `src/logbook.ts` is the Logbook module, in `Deps` as `logbook`: each Feature's decisions between its Sessions, one append-only JSON-lines file per Feature at `.factory/logbook/<id>.jsonl` (the id made safe as a file name), one entry per line with its time, kind, and the Ticket and Session where it has them. The kinds and their fields are one zod schema there; a line that does not parse is skipped. `build.ts` writes through `noteFor` (one Feature's writer, dated by `deps.now`): build started (the Go or the request for changes, branch, Workflow), setup ran, Ticket started, Ticket built (its commit), each red check with the gate report its fix round was handed, work thrown away onto an attempt branch and why, each Step's verdict (through the Workflow's `verdict`), the Review's verdict and issues, every Signal it puts on or takes off, the draft pull request, a pause and a hand-over to a person, each with why, and a fault that stopped the build, with where it happened and its stack trace, which goes nowhere else. The rounds outside the Ticket loop write through the same `note`: `feedback-round.ts` writes one `feedbackRound` entry per round (its Session, how it ended, the Feedback ids it answered, and those it left each with why, besides a `thrownAway` entry when it threw the round away, or a pause or a person stopped it, and kept an attempt branch), and `fixPullChecks` writes one `pullFix` entry per Pull-check fix round (the failing Pull checks, how it ended), a `thrownAway` entry with its Session when a round that gave up, paused or was stopped kept an attempt branch, and the hand-over to a person. `intake.ts`, another process, writes the same file through `fileLogbook`: `madeBySource` when a Source makes a Feature, `happenedAgain` when it comments so, and `standingGo` when a `go: true` Source assigns and gives the Go; a write that fails is said and never fails the delivery. It writes on a terminal or not, as the ledger is. Its adapters are the file, `fileLogbook`, and `memoryLogbook` in `src/fakes/logbook.ts`, which the build specs assert over; `src/logbook.spec.ts` is the one contract spec both run. `src/logbook-reader.ts` is the one reader the views use: `readLogbook(root, feature)` joins the Feature's Logbook with its Sessions from the ledger (kind, Ticket, outcome, cost, duration, and the transcript's path under `.factory/logs/`), in the order they happened; a Feature with ledger lines and no Logbook file reads as its Sessions only, with `recorded: false`. `readSession(root, id)` reads one Session: its whole transcript through `renderSession` in full mode and the ledger's lines for that id (a fix round resumes a Session, so there may be several), and gives null for an id that is not a Session id (`isSessionId`: letters, digits, `-`, `_`) or has no transcript. `nightjar ui` draws it at `/sessions/<id>` (400 for an id that is not a Session id, a plain 404 page for one with no transcript), and the "Building now" panel links to the Session being built. `nightjar ui` draws a Feature's Logbook at `/features/<id>` (the id percent-decoded, reaching a file only through `logbookPath`; 400 for one that does not decode, has a control character or is over 128 characters): each Session with its kind, Ticket, outcome, cost and duration, its summary folded (`sessionSummary`, the summary rendering) and a link to its page; each decision in the words of `src/logbook-text.ts` (`decisionText`, plain text the CLI can share), with what it holds folded (a red check's gate report, the Review's issues); the build in flight at the end; and a quiet note for a Feature with ledger lines and no Logbook file. The page opens `/features/<id>/events`, which pushes its content again whenever it changes, as `/events` does the Board's. Every Mat card, Table row and the "Building now" panel link to their Feature's Logbook, and the Overview's All Logbooks lists every Feature with a Logbook file or ledger lines, the one touched last first (`listLogbooks`). `src/logbook-command.ts` is `nightjar logbook FEATURE` and `nightjar logbook --session ID [--full]` (dispatched from `main.ts` like `ui`): it finds the repo root with git, reads `.factory/` through `readLogbook` and `readSession` and nothing else (no adapters, no login), and prints each Session as a line with its kind, Ticket, outcome, cost and duration under its transcript's path, each decision as `decisionText` words with what it folds printed beneath, and a Session as its text and a line per tool call, plus each tool result with `--full`; a Feature or Session with nothing recorded gets a plain message and exit 1, a bad argument exit 2. Nothing of the Logbook leaves the machine.
- `src/measures.ts` is the Measures of `nightjar ui` (a Measures panel, drawn by `measuresPanel` in `src/ui.ts` with `dollars` and `elapsed` from `view-text.ts`): `measures({ entries, logbooks, pullStates, now })` is a pure function from the ledger's lines, every Feature's Logbook (`readEveryLogbook` in `src/logbook-reader.ts`) and what the Code host said of each pull request, to Autonomy, the median Time to pull request, the median Cost per pull request and the Sessions by outcome, over the 30 days up to `now`. The pull requests are the Logbooks' `pullOpened` entries, one per url, each with its claim (the `buildStarted` before it) and draft times and the cost of its Feature's Sessions in the ledger between the claim and the draft, plus the rounds after the draft (Feedback, Review, Pull-check fixes) up to the next claim or draft. The Sessions are counted by `outcomeKind` (done, failed, paused, stopped, questions, gave up), since a ledger outcome carries free text. Autonomy is the share of merged pull requests whose commits all carry a `Factory-` trailer (`hasTrailer` in `src/publish.ts`, the test Publish uses; Nightjar commits under the person's own git identity, so an author's name cannot tell its commits from a person's). The Code host's optional `pullState(pull)` (`PullState`: merged or not, and the pull request's commits) feeds it; a Code host without it, or a page given no Code host, gives `unavailable` and the panel says why instead of showing Autonomy. `src/measures-cache.ts` is `.factory/measures.json`, what `refreshPullStates` last read: it asks the Code host at most once an hour (the time of the last read is in the file, a failed read included), never again about a merged pull request, keeps the last state of one it fails on and writes why, and drops pull requests that left the window. A pull request's id is taken from the last number of its url (`pullOfUrl`). `src/ui-measures.ts` is the watch that calls it when the page opens and once a minute (`watchMeasures`, like the Tracker's), and `measuresView`, which reads `.factory/` only and gives the panel its numbers and its note. The contract suite for `pullState` is `src/contract/pull-state.ts`; its harness's drafts world needs `merge`.
- `src/retro.ts` is `nightjar retro [--create]` (its arguments in `src/args.ts`, dispatched from `main.ts` after the same `preflight` a build runs): `failuresIn` picks the ledger's lines of the last 30 days (`MEASURE_DAYS`) that failed or handed their work back (`isFailure`: a `failure` field, or an outcome that failed, gave up, was blocked or asked questions; never a pause, a person's stop or another Retro), and `runRetro` hands the latest 20 (`failureOf`, each with the last 30 lines of its transcript in `renderSession`'s full mode, each cut to 400 characters and all to 3000) to one Session through the Coding agent's `retro` kind. That kind runs in the main checkout on the review's tools and settings (`REVIEW_TOOLS`, `reviewSettings`: no Edit or Write, Bash only for git's read commands, the deny rules untouched) and no plugins; its prompt (`retroPrompt` in `prompt.ts`) lists the categories to look for, most severe first, and its schema (`RETRO_SCHEMA`) answers `proposed` with a Feature file's text or `nothing`. With no failure it says so and starts no Session. It checks the day's spend first (`dayOver`, and `allowance` for what is left of `dailyUsd`), runs on at most the review's $3 and 10 minutes (`RETRO_USD`, `RETRO_MINUTES`), and records the Session in the ledger as step `retro` with an empty feature and branch, so it counts against the day; `listLogbooks` skips those lines. The answer is checked with `readFeatureFile` and written to `.factory/plans/retro-<date>.md` (`retroFile`, `-2` and on when the day's file exists); with `--create` it is made through the Tracker's `FeatureWriter` (`makeFeature` in `create.ts`), with no Signal, and a Tracker that cannot make Features is refused before the Session starts. The build loop's `Deps` hold the Coding agent without `retro`, and a build's ledger lines (`LogEntry`) never carry it.
- `src/worktree.ts` is the worktree seam, in `Deps` as `openWorktree`: a `Worktree` is what the loop, the Workflow's Steps, a Pull-check fix, a Feedback round and a Review round do to the Feature's branch (`head`, `commitTicket`, `commitStep`, `commitPullFix`, `commitFeedback`, `commitReview`, `built`, `stepsDone`, `pullFixes`, `answeredFeedback`, `headTrailers`, `toRemote`, `pushOutcome`, `setAsidePush` and `holdsUnpushedTicket` (after a push that failed: the remote holds the commit, a person pushed, or a fault; a person's push sets Nightjar's commits aside on `-attempt-push`, and a fault does so unless an unpushed Ticket commit lies on the branch), `ahead`, `diff`, `notes`, `revert`, `discard`, and the setup mark), and `OpenWorktree` opens one. Its real adapter, `GitWorktree` through `openWorktree` (git in the Feature's worktree under `~/.nightjar/worktrees/`), also words the commits (`ticketCommitMessage`, `stepCommitMessage`) and names the side branch (`attemptBranch`) that the in-memory adapter, `memoryWorktrees` in `src/fakes/worktree.ts`, reuses. `src/build.spec.ts` runs over the in-memory one, where a spec plays the Session with `write`; the specs about commit, discard and cleanup keep real git (`makeGitWorld`), and `src/worktree.spec.ts` is the one contract spec both adapters run.
- Around the loop: `session.ts` (one headless `claude -p`), `settings.ts` (the agent's allow list from config, and the deny rules and the sandbox config cannot loosen: every Session's settings come from there, with no network and no hooks), `check.ts` (the repo's check command) and `gate.ts` (the gate report a red check hands the fix rounds and the pull request, built from `factory.json`'s `gate`), `prompt.ts`, `next-step.ts` (the Next step that ends each comment Nightjar leaves for a person, by the Signal names `factory.json` sets), `status-note.ts` (the Status note's words, ADR 0012: one pure function from the state word, a sentence, the Tickets, the pull request, the Next step, the earlier runs and the Logbook line to the Markdown `build.ts` hands the Tracker's optional `statusNote`; its `STATE_WORDS` are the Board's state words, one table for the note, the pull request and the page; its `waitingCommentText` is the new comment a person who is needed gets, which stands on its own: the **Waiting on you** headline, the cause in a few lines, an `excerptOf` the output (at most 15 lines, colour codes stripped) only while no pull request holds it, else a link to the pull request's section, the Next step, the Logbook line and the footer. `build.ts` posts it for every Feature or Ticket it hands to a person and then writes the Waiting on you note; `Tracker.comment` may resolve with the comment's web address, which the note's Ticket list links. A pause and a person's stop write the note alone, Paused (until the time `--watch` tries again, `Deps.pauseMs`) or Stopped; a Tracker without `statusNote` gets the comments it got before), `fault.ts` (a fault that stops a build: `buildFeature` and `fixPullChecks` throw it as a `BuildFault` naming where it happened, from setup to a Pull-check fix, after writing it to the Logbook with its stack trace; `handBack` in `queue.ts` gives the Feature needs info, a comment from `faultAsk` (the place, the cause, and whether giving the Go again is likely to help, `passingFault`) and the Waiting on you note, with no stack trace), `plan.ts` (Build order), and `ports.ts` (the lock scheme that reserves `ports` per run, held until the process ends), and `ledger.ts` and `status.ts` (`.factory/runs.jsonl` and `.factory/status.json` in the repo; `status-shape.ts` is the file's shape, and `status-reader.ts` reads `.factory/` into what a live view shows: status, stopped, session tail, Completed), and `stale.ts` (the idle `--watch` check for newer Nightjar code: a newer installed or published version, or `origin/main` ahead of a linked checkout; a read only that never fails a watch). `src/ui.ts` is the page `nightjar ui` serves (`src/ui-theme.ts` holds its themes: Paper, the default, and the Nightjar stylesheet in `ui.ts`, each a whole stylesheet, switched in the bar and kept in local storage; `src/ui-command.ts` the command; `src/ui-banner.ts` holds the banner image as a `data:` URI, which the CSP's `img-src data:` allows): `node:http` on 127.0.0.1, GET and HEAD only, panels rendered from the reader and pushed as server-sent events when a file under `.factory/` changes. It reads the Tracker as well as `.factory/` (ADR 0009): `src/ui-tracker.ts` builds the Tracker from `factory.json` as a run does (`makeAdapters`), for config.json's `assignee` else the signed-in person, and holds it as a `ReadingTracker`, the read methods only. It reads the Queue (`assignedFeatures`), Waiting on you (`waitingOn`) and their `ticketCounts`, Nightjar's open pull requests (the Code host's `openPulls`, by each body's Feature marker) to count the Tickets a Feature's branch built, which stay open on the Tracker until it merges, and the Shelf (`shelf(person, SHELF_MAX)`, the fifth Mat; a Tracker without it shows "Shelf is not available from this Tracker"), when the page opens and every 60 seconds (`watchTracker`, `TRACKER_EVERY_MS`), one read at a time, never on a file change. A failed read keeps the last lists, which the header marks with their age. Those lists take the place of `status.json`'s; the run's waiting Tickets and Building still come from `.factory/`. A Feature's title on those three opens the Feature detail panel (`src/ui-feature.ts`, a `<dialog>` outside the panels each event replaces): `GET /feature?id=…` reads `feature` and `tickets` through the same Tracker (`detailFrom`, `readFeature`), puts the Tickets in Build order (`buildOrder` in `plan.ts`) and answers the panel's markup, which ends with the Feature's Logbook section (`logbookSection` in `ui.ts`: `readLogbook` over `.factory/` alone, each Session's entry opening its transcript at `/sessions/<id>` in a new tab, an empty state with no Sessions; it shows on a 502 too, as the Logbook is on this machine), or a 502 with the fault and a link to the Feature on the Tracker. Tracker text goes through `src/markdown.ts`, a small Markdown subset that strips raw HTML and escapes everything else, so a body puts no tag, script or event handler on the page; `acceptanceCriteria` in `ticket-contract.ts` cuts each Ticket's criteria out of its body. `view-text.ts` holds what the page and the terminal both say: clocks, money, ids and the run's state. On a terminal `live.ts` redraws the block of `live-view.ts` (a pure function from the reader's result and a width) each second, and appends the lines `say` is given to `.factory/nightjar.log`.
- Specs sit beside their code as `*.spec.ts`. `src/fakes/machine.ts` is a whole machine of stand-ins (git checkout, `gh`, `az`, `claude`, and `bwrap` and `socat` for the sandbox check, alone on the PATH; `FAKE_BWRAP_BLOCKED` plays a bwrap that AppArmor refuses), with the one `claude` that `src/cli.run.spec.ts` (the real command end to end, `nightjar retro` too), `init` and `doctor` share; its `gh` opens every issue as #7, for `nightjar retro --create`. `Host` carries the `gh` runner beside the Azure DevOps `request`, so a spec passes a `FakeGitHub` as it passes a `FakeAzureDevOps`.
