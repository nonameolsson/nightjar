# Architecture

The module map of Nightjar. Words are in [GLOSSARY.md](../GLOSSARY.md); decisions in [docs/adr/](adr/).

- `src/build.ts` is the build loop: one Feature from the Go to a draft pull request. It talks only to the `Tracker` (`src/tracker.ts`) and `CodeHost` (`src/code-host.ts`) interfaces, starts every Session through `codingAgent` (`src/coding-agent.ts`) and branches only on its outcomes, and speaks of Signals (`src/signals.ts`), never label names.
- `src/github/` holds the GitHub adapters, the only code that calls `gh` (a lint rule holds this). `src/fakes/` holds the in-memory Tracker and Code host the build loop's specs run over; those specs fake the Coding agent with outcomes.
- `src/footer.ts` is the footer every comment and reply of Nightjar ends with, and the one test that tells its words from a person's: a Code host's `feedback` leaves out whatever ends with it. `src/github/trust.ts` is the one trust rule of the GitHub Tracker's comments and the GitHub Code host's feedback; `src/check-output.ts` cuts a failed check's output to its last 4 KB.
- `src/azure-devops/` holds the Azure DevOps adapters, the only code that calls Azure DevOps: `sign-in.ts` (the `az` token, else `AZURE_DEVOPS_EXT_PAT`), `api.ts` (the one signed-in HTTP layer, with a request seam), `index.ts` (`openAzureDevOps`, one API every Azure DevOps adapter shares), `tracker.ts` (Boards), `code-host.ts` (Azure Repos; it links work items when `src/adapters.ts` pairs it with Boards of the same organization, else names Tickets in the body), and `fake-azure-devops.ts`, the in-memory Azure DevOps its specs run the real adapters over.
- `src/config.ts` loads and validates `factory.json`; `src/person-config.ts` the person's own optional `~/.config/nightjar/config.json` (`dailyUsd`, `assignee`), found through the injected env; `src/adapters.ts` builds the adapters `factory.json` names. `src/adapter-module.ts` loads a repo's own adapter from a `type: "module"` entry and refuses one that lacks an export or a method (`docs/custom-adapters.md`).
- `src/contract/` is the Adapter contract suite (`feature-writer.ts` is the creation suite, run over a Tracker that also implements the optional `FeatureWriter`; `waiting-on.ts` the suite for the optional `waitingOn`; `ticket-counts.ts` the suite for the optional `ticketCounts`; `feedback.ts` the suite for a Code host's optional `feedback` and `reply`); `run.ts` runs it without a test runner and `command.ts` is `nightjar contract MODULE` (the module exports `trackerHarness` and/or `codeHostHarness`).
- `src/main.ts` is the command (`src/cli.ts` runs it); `runNightjar(argv, host)` takes the platform, env, cwd, and init's `ask` and `prompter` from a `Host`, which specs inject. It stops every command on `win32` first. `src/queue.ts` picks the next Feature for `--once` and `--watch`.
- `src/checks.ts` lists the checks in order (API key, Node, checkout, `factory.json`, Tracker and Code host logins, `claude` installed and signed in, commit signing, each Workflow's skills), each naming the facts it needs from the ones before it; `src/check-runner.ts` runs them into lines, skipping a check whose need is missing, and `checkMachine` turns what they found into `Ready` or a refusal. The fix a Tracker or Code host failure needs (`gh auth login`) comes from its adapter, as `Adapters.trackerFix` and `codeHostFix`. A build stops at the first failure, `src/doctor.ts` (`nightjar doctor`, alias `--dry-run`) runs all and lists them, and `src/init.ts` (`nightjar init`, select prompts on a terminal through `src/prompter.ts`, else answers on stdin through `src/ask.ts`) shows what it is about to do and asks to go on, then writes `factory.json`, calls `Adapters.prepareSignals` (`src/github/labels.ts` creates the labels) and then runs the same checks.
- `src/create.ts` is `nightjar create FILE`: `src/feature-file.ts` reads a Feature file in the shape of `docs/ticket-contract.md` (checking each Ticket through `src/ticket-contract.ts`, the same check `ticketFaults` runs on a Ticket's body), and the configured Tracker makes it through `FeatureWriter`. `skills/nightjar-feature/` is the Claude Code skill the package ships, which writes that file.
- `src/workflow.ts` is the Workflow module: it picks a Feature's Workflow (its `**Workflow:**` line, else `defaultWorkflow`), and its `WorkflowRun` runs the Steps at a point (after each Ticket, or after all of them before the review) and keeps their reports for the pull request's section. It owns a Step's rounds, `until`, budget, serve command, and its end: its own commit with a `Factory-Step` trailer, or thrown away. `build.ts` calls it at those two points and branches only on whether the run goes on, pauses or stops; it lends the Steps its fix rounds, ledger and status file. `serve.ts` starts a Workflow's serve command, `skills.ts` lists the skills a headless session loads (`checks.ts` checks each Step's `/skill` against them, per Workflow), and `settings.ts` adds a Workflow's commands, tools and localhost network to its Steps without touching the deny rules.
- `src/coding-agent.ts` is the Coding agent module: `codingAgent(setup, session)` starts a Session for a Ticket's build, a fix round, a Step round or the review, and says how it ended (`failed`, `paused` and `aborted` for every kind, besides the kind's own answer). It owns each kind's prompt, schema, tools, settings and model and effort (a CLI flag, then the work's own setting, then the repo's defaults); the deny rules stay in `settings.ts`, and the questions comment in `prompt.ts`.
- `src/spend.ts` is the Spend module, in `Deps`: it records each Session's cost as a ledger `Entry` and answers `dayOver(now, dailyUsd)` (the pause's words) and `allowance(cap, spent)` (what a piece of work may still spend, and whether that is enough for another Session); the cap arithmetic lives there alone. Its adapters are the file, `fileSpend` in `src/ledger.ts` (`.factory/runs.jsonl`, whose format and `ledgerPath` stay there), and `memorySpend` in `src/fakes/spend.ts`, which the build specs assert over; `src/spend.spec.ts` is the one contract spec both run. `StatusFile` reads the day's spend through it. `status-reader.ts` and `ui.ts` read the file's lines for the live views.
- `src/worktree.ts` is the worktree seam, in `Deps` as `openWorktree`: a `Worktree` is what the loop and the Workflow's Steps do to the Feature's branch (`head`, `commitTicket`, `commitStep`, `built`, `stepsDone`, `ahead`, `diff`, `notes`, `revert`, `discard`, and the setup mark), and `OpenWorktree` opens one. Its real adapter, `GitWorktree` through `openWorktree` (git in the Feature's worktree under `~/.nightjar/worktrees/`), also words the commits (`ticketCommitMessage`, `stepCommitMessage`) and names the side branch (`attemptBranch`) that the in-memory adapter, `memoryWorktrees` in `src/fakes/worktree.ts`, reuses. `src/build.spec.ts` runs over the in-memory one, where a spec plays the Session with `write`; the specs about commit, discard and cleanup keep real git (`makeGitWorld`), and `src/worktree.spec.ts` is the one contract spec both adapters run.
- Around the loop: `session.ts` (one headless `claude -p`), `settings.ts` (the agent's allow list from config, and the deny rules config cannot loosen), `check.ts` (the repo's check command) and `gate.ts` (the gate report a red check hands the fix rounds and the pull request, built from `factory.json`'s `gate`), `prompt.ts`, `next-step.ts` (the Next step that ends each comment Nightjar leaves for a person, by the Signal names `factory.json` sets), `plan.ts` (Build order), and `ports.ts` (the lock scheme that reserves `ports` per run, held until the process ends), and `ledger.ts` and `status.ts` (`.factory/runs.jsonl` and `.factory/status.json` in the repo; `status-shape.ts` is the file's shape, and `status-reader.ts` reads `.factory/` into what a live view shows: status, stopped, session tail, Completed), and `stale.ts` (the idle `--watch` check for newer Nightjar code: a newer installed or published version, or `origin/main` ahead of a linked checkout; a read only that never fails a watch). `src/ui.ts` is the page `nightjar ui` serves (`src/ui-command.ts` the command; `src/ui-banner.ts` holds the banner image as a `data:` URI, which the CSP's `img-src data:` allows): `node:http` on 127.0.0.1, panels rendered from the reader and pushed as server-sent events when a file under `.factory/` changes. `view-text.ts` holds what the page and the terminal both say: clocks, money, ids and the run's state. On a terminal `live.ts` redraws the block of `live-view.ts` (a pure function from the reader's result and a width) each second, and appends the lines `say` is given to `.factory/nightjar.log`.
- Specs sit beside their code as `*.spec.ts`. `src/fakes/machine.ts` is a whole machine of stand-ins (git checkout, `gh`, `az`, `claude` alone on the PATH), with the one `claude` that `src/cli.run.spec.ts` (the real command end to end), `init` and `doctor` share. `Host` carries the `gh` runner beside the Azure DevOps `request`, so a spec passes a `FakeGitHub` as it passes a `FakeAzureDevOps`.
